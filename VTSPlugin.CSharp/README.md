# VTSPlugin.CSharp
This is a core library for all the other ones.

It outlines overall architecture which all the other libraries will have to follow.

API is defined via the interfaces, but libraries can choose to optimize specific use cases via interface devirtualization.

Library also handles concurrency, but it uses locks for this.
Future updates will optimize access to shared data in concurrent contexts are new ideas for this arise.
Feel free to suggest your own as well.

### `IVTSPlugin`
Describes all the info an overall plugin might have.
Modifying plugin info is possible, but depending on the implementation, changes might apply only after reconnecting to VTube Studio.

### `IVTSEndPoint`
Mostly dormant info about VTube Studio application instance.
Has a lifetime tracker based on keep-alive packets, allowing you to check if a target VTube Studio instance is still present.

Can be forcefully killed by using a `Kill` method explicitly.
This will kill any `IVTSSocket`s using this `IVTSEndPoint`.

### `VTSPacket`
Basic class for all request/response/event packet types.

New packet instances can be created via `VTSPacketPool.Shared`, and `VTSPacket`s are reset when returned to the pool.

Using `ToString` on all `VTSPackets` will return their readable representation.
In v1 it will be JSON, but in further versions it will be custom low allocation encoder.

### `IVTSDiscoveryService`
Responsible for listening on a VTube Studio broadcast UDP port `47779`.
There, VTube Studio tells about active VTube Studio instances.
All found connections are translated into a `IVTSEndPoint` for you to track.

### `IVTSSocket`
A WebSocket implementation managing a connection with a given `IVTSEndPoint`.
Capable of sending and receiving raw byte data, and notifies about connection being closed by a remote host.
Returns info as disposable raw byte memory blocks, allowing `IVTSSocket` user to do basically anything with it.

Incapable of analyzing the packets themselves.

### `IVTSConnection`
Connection instance, connected to a specific `IVTSEndPoint`.
Manages `IVTSSocket` under the hood.

Generates and tracks RequestIDs for each new request.

Capable of sending, receiving and analyzing `VTSPacket`s.
Packet deserialization is usually offloaded to a caller via `JsonResult<T>` struct.
```C#
using var result = await Connection.Request<VTSAPIStateResponseData>(VTSAPIStateRequest.Instance);
using var scope = result.TryUnpackScoped();
if (scope.Successful)
{
	Console.WriteLine($"API State:\n{scope.Data}")
}
else
{
	Console.WriteLine($"Request failed! ErrorID: {scope.ErrorID}, Message: {scope.ErrorMessage}");
}
```

# Tasks
Since Godot and Unity use different type of tasks - VTSPlugin.CSharp adapts by using aliases and conditional compilation.
- In Godot - `GDTask` is used.
- In Unity - `UniTask`.
To implement this, all tasks are surrounded with preprocessor arguments.

This allows us to control which task is used, with a cost of making it tedious to expand the library.

Note: If possible, will be better to write our own pre-processor, or in any other way replace a type of a task used to GDTask.
For now we default to UniTask.
